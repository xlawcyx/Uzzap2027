==================================================
2. INCOMPLETE OR WEAK FUNCTIONS
==================================================

UzzapRepository.kt:

- acceptFriendRequest()
  Updates local data but does not fully update the Firestore request or create a reciprocal friendship.

- declineFriendRequest()
  Removes local data but does not update or delete the Firestore request.

- deleteContact()
  Removes the contact locally but does not remove the cloud relationship.

- blockUser()
  Removes the local contact but does not persist a blocked-user record locally or in Firestore.

- sendMessage()
  Uses a fallback recipient when conversation data is missing. Failed messages are not queued or retried.

- sendRoomMessage()
  Sends remotely without exposing success or failure to the caller. There is no sending or failed state.

- joinOrLeaveRoom()
  Changes local membership and chatter count but does not persist actual user membership in Firestore.

- createChatroom()
  Can create local data even when the Firestore operation fails. There is no rollback or clear UI error.

- submitReport()
  Does not return a success or failure result to the UI.

- deleteAccountData()
  Does not fully delete conversations, inbox messages, friend requests, reports, room messages, or room memberships from the cloud.

UzzapFirestoreService.kt:

- listenToUserInbox()
  May process existing inbox documents repeatedly and deletes documents immediately, which can cause duplicate processing or message loss.

- listenToFriendRequests()
  Emits all pending requests on every snapshot and does not acknowledge requests after acceptance or decline.

- listenToChatrooms()
  Does not clearly handle an empty remote result, so stale local rooms may remain.

- sendFriendRequest()
  Does not return a Result. Failures are only logged.

- createChatroom()
  Runs asynchronously and hides failures from the caller.

- sendRoomMessage()
  Runs asynchronously and hides failures from the caller.

- updateRoomChatterCount()
  Does not expose success or failure and has no retry path.

- submitReport()
  Does not await the Firestore write and has no validation, result, or retry behavior.

- deleteUserCloudData()
  Deletes only limited profile documents. Most user-owned remote data remains.

- cleanUp()
  Listener cleanup exists, but listener ownership is not fully centralized. Repeated initialization may create lifecycle problems.

UzzapViewModel.kt:

- deleteAccount()
  Does not provide a clear success or failure state, swallows errors, and does not clearly complete sign-out after deletion.

- cloudPresenceSync setting
  The preference is stored but does not appear to enable or disable presence synchronization.

- notificationsEnabled setting
  The preference is stored, but notification behavior is not implemented throughout the app.

- soundEffectsEnabled setting
  The preference is stored, but sound behavior is not implemented throughout the app.

- autoSaveHistory setting
  The preference is stored, but its behavior is not consistently implemented.

- Offline authentication
  Offline sign-in/sign-up can create or access local users without real password verification. This must be restricted to debug/demo builds.

UzzapDatabase.kt:

- Database migration
  fallbackToDestructiveMigration(dropAllTables = true) can erase all local data after a schema change. Explicit migrations are needed before production release.

==================================================
3. CONFIGURATION AND SECURITY CONCERNS
==================================================

- Demo-user auto-provisioning should not be enabled in production.
- Usernames and authentication-related information should not be logged in release builds.
- Input validation should be centralized for messages, contacts, rooms, and reports.
- Firestore rules and Kotlin serialization must remain aligned for fields such as authUid, senderUid, recipientUid, participantUids, and createdByUid.
- Account deletion should be tested against both Firebase Auth and Firestore.

==================================================
4. RECOMMENDED PRIORITY
==================================================

1. Restore the Gradle wrapper and establish a reproducible build.
2. Add and verify google-services.json for the intended Firebase project.
3. Implement explicit Room migrations.
4. Complete cloud relationship management for friends, blocks, rooms, and messages.
5. Implement complete account deletion and remote data cleanup.
6. Return Result or state values from Firestore write operations.
7. Centralize and safely dispose of Firestore listeners.
8. Restrict offline authentication and demo users to debug/demo builds.
9. Add Firebase Emulator tests and Firestore rules tests.
10. Implement all stored settings or remove settings that do not have behavior.
